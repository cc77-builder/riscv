# 两条开发线、三人协作：建议先试行，不冻结Issue方案

> **2026-10-13 后续讨论更新：** 当前执行约定见 [三人两线协作机制](../../docs/collaboration-current.md)。保留独立工作区、START/RELEASE/ACK、固定 SHA 与普通快进 Push；明确**不依赖 GitHub Actions**，允许团队 Issue/Discussion 或单份 Markdown 作交接主记录，并加入个人 Fork **按需、非实时、安全快进同步**。以下继续保留 Pro 设计时的方案比较，不能解读为已部署锁服务或自动化。

本轮只交付设计和模板，未删除分支、指定真人负责人、创建假进度Issue、修改权限或部署后台服务。这里把“2分支”暂解释为**两条活跃开发线，main仍是稳定集成线**；若你们要求总共只能有两个远端分支，需要另行调整。分支具体名称、两人组合、值班时间和唯一协调仓库待团队确认。

## 1. 首先分清四种身份

| 身份 | 持续多久 | 解决什么问题 |
|---|---|---|
| 模块负责人 | 一个工作包生命周期 | 谁负责结果与设计判断 |
| 当前执行者 | 一次开发/测试会话 | 此刻谁在做哪项工作，包括其Codex任务 |
| 共享分支推送者 | 一次明确交接窗口 | 谁可以推进该远端分支及对应工作区 |
| 评审/验收者 | 指定提交和证据 | 谁独立检查哪一个SHA，而不是模糊的“最新代码” |

Issue上挂一个assignee只能很好地表达第一种身份。**有负责人不等于正在执行；正在执行不等于有权改变共享分支。** CODEOWNERS主要路由评审，也不是模块互斥锁。依据[S23/S25](SOURCES.md)。

## 2. 方案比较与推荐

| 方案 | 优点 | 不足 | 建议 |
|---|---|---|---|
| 每人开始时发一个Issue评论 | 最简单、有时间线 | 同时认领、忘记结束、跨fork记录分裂；无互斥保证 | 只当通知，不单独承担交接 |
| 每个工作包一张任务卡＋一条共享分支接力记录 | 责任与当班者分离；维护少；适合三人 | 属于协作约定，不能防恶意/绕过操作 | **首选试行** |
| Issues + Projects字段/看板 | 能按模块/人员/状态查看同一记录 | 字段多会增加维护；不产生锁 | 卡片数量增加后再开；不重复维护进度 |
| 在唯一canonical Git分支提交机器可读占用状态 | 可用正常push对同一起点竞争做仲裁 | 元数据提交和异常恢复有成本；仍可绕过 | 需要机器判定时再加，不默认上锁服务 |
| 独立数据库/机器人/周期Actions发放锁 | 可实现更多约束 | 运维、凭据、费用与故障点超出三人初期需要 | 暂不采用 |

**推荐：工作包卡片 + 明确交接 + 固定SHA评审 + 普通快进push。** 卡片可放团队仓库Issues，也可先用已有进度文档；只选一个主记录。交接可以是一条常驻Issue/Discussion里的结构化评论，不必为每次上班新建Issue。通讯软件只提醒并贴链接，不另外维护一套状态。

这不是证明Issue最好，而是目前规模下低成本、容易执行的起点。先试两个完整交接周期，再依据冲突、等待和维护负担决定是否上机器可读占用记录。

## 3. 分支按交付链划分，人员不必按分支长期绑死

建议抽象为H（硬件接入线）与SV（语义/软件/验证共享线）：

- H：一个当期主要开发者负责译码、FU适配、写回及跨模块接口；减少高冲突热文件的多头修改。
- SV：另两人错峰推进语义/参考模型/强基线，以及独立测试/测量/应用内核。两人都有明确工作包，不是一个人工作、另一个人纯等待。
- 三人都对自己改动交模块测试和证据；独立复核交给另一人，不能把全部测试、文档和集成都压给第三人。

H/SV只是职责线，不是已创建的分支名，也不暗示哪位成员对应哪个历史分支。按成员实际能力，可把组合调换。常见热文件包括译码、FuConfig、EXU/写回、合同及版本锁；同一时段只安排一个主编辑者，其他人给建议或限定补丁。

**共享远程分支，不等于共享本地目录。** 两人各用独立clone/worktree和独立输出目录。非推送者可在固定SHA上评审、跑测试、准备下一任务；同时修改同一工作树/索引或让构建读取不断变化的源码并不安全。detach工作树不增加活跃远端开发分支。

## 4. 一次班次的最小流程

### 开始前

读任务卡和最近交接，确认canonical仓库、分支、上一交接SHA、当前推送者、未结束Codex/构建任务。上一人明确release且下一人确认接收后才能取得推送窗口；到达预计结束时间**不自动获得抢占权**。

检查本地根仓库、相关外部NEMU工作区与子模块状态；保留未提交/未跟踪文件，不用reset --hard或自动stash掩盖它们。读取远端后，在共享跟踪分支上只接受明确的快进更新。已有分叉或未发布提交时停止自动流程，先比对，不把“pull失败”当作允许force的理由。

在任务卡写一条START：执行者、任务ID、允许路径、起始SHA、实际开始时间（带时区）、预期交接窗口、关联Codex任务/回执。计划时间和实际时间分开。未开始的任务保持ready，不能批量标成doing。

### 开发中

只修改约定范围；跨合同/编码/公共接口变更先同步。编译/仿真记录源码SHA、NEMU SHA/补丁、子模块、工具版本、命令和配置。长构建固定源码快照及输出目录，不能在交接后继续读取被下一班修改的工作树。

本机Codex直接操作Windows文件和Git；ChatGPT通过GitHub连接器研究已授权仓库，需要检查或启动本机任务时才使用ChatPC。**Codex本身不依赖ChatPC才能读取本机文件。**

### 结束与交接

提交小而可解释的变更，检查diff范围、测试和未完成项；普通push到明确的canonical开发分支，重新查询远端SHA。发布RELEASE记录：最终代码SHA、实际做了什么、测试通过/失败/未运行、日志位置、剩余风险、下一步、仍在运行的任务。编译没完成时可以交接，但必须清楚标WIP/未验收，不能变成“完成”。

下一人回复ACK，确认实际检出交接SHA和自己的任务范围，再START。上一人及其自动化任务此后不能继续推进共享分支。离线或失联时由两人明确确认恢复方案，保留旧工作；不要靠计时器静默抢锁。

## 5. 同一分支与PR的隐蔽冲突

后一个人push会改变从该共享分支发出的未合并PR。不能让“上一班已评审通过”自动覆盖下一班新代码。

首选每批小交付完成评审/合并后再推进下一个批次。若共享分支仍有待审PR，冻结对该PR head的继续push；下一班可在独立本地工作树准备代码，待PR结束再显式整合。需要允许PR更新时，重新绑定评审和测试到新SHA，不沿用旧批准。不要为规避这一点偷偷增设未约定的第三条活跃远端开发线。

对尚未准备创建PR的工作，也可先做固定SHA评审；真正合并时必须再次验证被合并的提交集合、base与最终树。main同步进入共享线是一项显式集成任务，不是随手rebase已经共享的历史。

## 6. Issue/看板怎么保持清楚而不膨胀

每张卡对应可验收工作包，不对应“今天上班”。最小字段：任务ID、模块、长期负责人、状态、依赖、允许路径、起点/验收SHA、下一步。状态建议 ready / active / blocked / review / verified；暂停或交接不表示任务已完成。blocked必须有阻塞原因与解除条件，不用“完成80%”替代证据。

每人最多一个主要active实现任务；可并行做独立评审/固定快照测试，但明确资源占用。Projects只作为同一卡片的按人/模块视图。原来的T00/T06/T07/T08/T09等任务号继续保留，下面工作包是细化，不重建一套与旧计划冲突的编号系统。

**协调主记录必须三人都能访问，且只有一个canonical位置。** `LiZufan001/riscv`与`cc77-builder/riscv`的Issues不是自动镜像。本轮把模板放在个人Fork只是交付材料，不能据此声称团队共享分支已被某人锁定。

## 7. 更严格的可选机制：Git占用记录

仅在试行后确有需要时启用：canonical共享分支上保存一个简短占用文件，记录released/held、持有人、会话ID、起始SHA、任务和计划交接时间。两人从同一head创建不同claim提交，普通push通常只允许一个推进该引用；失败者必须fetch并重新读占用状态，**不能把自己的claim重放/合并到赢家后面来抢占**。

本轮临时Git实验还验证了两个反例：读到新head的人即使不是持有人，直接推一个后继提交仍可能被Git接受；在两个fork里分别claim也都能成功。故该方案仍依赖守约或额外服务端权限/检查，不能称为不可绕过的锁。计划结束时间不是自动TTL，避免“旧进程还在写、新人已经接管”。

不使用force-with-lease作为日常交接方法；它解决的是引用更新条件，不自动提供模块责任或代码语义正确性。

## 8. 从三条开发线收敛的迁移清单

1. 先确认两条线的名字、成员组合、main是否另计、协调记录放哪；读取团队远端的所有最新SHA，而非只看Fork快照。
2. 列出三条旧线各自独有提交/文件，区分RTL、NEMU补丁、模型、测试和文档。保存头SHA与迁移去向；未整合提交不能直接删掉。
3. 在新职责线按小批次显式整合，先审语义/接口，再执行相关回归。模型可以保留两个独立实现，不强行合成一份同源oracle。
4. 以可复现的组合版本验收；旧线先标只读/停用，不立即删除。真正删除/重命名另经团队确认。

## 9. 试行的成功条件

以两个完整交接周期观察：丢失/覆盖他人提交为0；同时误写同一工作区为0；每次交接都有可取回SHA和证据状态；三人无需私聊就能找到当前执行模块；记录负担不妨碍开发。若主要问题是并发抢占，再加机器可读claim；若主要问题是等待评审或过度串行，先缩小交付批次、增加固定SHA离线验证，不急着加更多锁。
