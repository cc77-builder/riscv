## 2. 反压为什么没有形成

### 2.1 实际仲裁存在，并非ready被绑高

本轮额外对照候选构建的`GENERATED.json`：`WbDataPath.sv`、`RealWBCollideChecker_2.sv`、`RealWBArbiter_14.sv`、`ExeUnit_17.sv`以及直接连接它们的`Backend.sv`/`ExuBlock_2.sv`六份生成文件全部匹配；EMU也匹配同一份生成清单。源码17份仍与R3记录身份一致，配置是MinimalConfig，不套用MinimalSimConfig。详见[SOURCE_PINS.json](SOURCE_PINS.json)与[带行号节选](analysis/SOURCE_EXCERPTS.md)。

实际路径如下：

- VFEX4为fromExu_17 / fromVfExu_2_0，接向量写回仲裁器输入6；FEX0为fromExu_8 / fromFpExu_0_0，接输入1。
- 两者在向量写回口3汇合：FEX0进入局部仲裁器输入0，VFEX4进入输入1；FEX0优先。
- 生成RTL的低优先级ready为`!high_valid || !low_valid`。对本次正常VDOT（vecWen=1、v0Wen=0、outvalid=1），可化为`VFEX4.ready = !FEX0_vector_write_valid`。
- 子VDot的out.ready直接继承父级io.out.ready。77个有效输出周期ready均1，所以这些周期没有FEX0有效向量写回请求与VDOT同时竞争。这是日志与实际组合逻辑合起来的结论，不是假定F2v完全没有执行。

### 2.2 为什么连续A/B没有自动填满P

一拍候选满足：`rReady = !liveR || out.ready`；`directR = in.fire && !liveP && rReady`；`enqueueP = in.fire && !directR`。P初始为空且R每次均可出槽，B到达的同拍A输出，B直接替换R。P只在已有R不能输出、另一个事务仍获准接收等条件下承担缓冲。本次缺少那个输出受阻周期，不是点积算术错误或P状态丢失。

### 2.3 M1缩短了释放链，但没有建立仲裁重叠保证

M1将`fmv.x.w`提前，并用`vadd.vx v8,v8,t6`替代旧的输入释放步骤。fdiv产生ft0后，F2v压力依赖ft0；VDOT输入还要经过浮点转标量、可选xori、标量转向量、向量加法的RAW链。

关键是`vadd.vx`在真实译码中不是一个零延迟旁路：VEC_VXV先生成I2v临时向量，再由向量ALU写v8，VDOT等待新v8。`vfmv.v.f`也由F2v临时向量及后续向量微操作组成。“8条vfmv在源码中相邻”不等于“写回口3被连续占用8拍”。I2v/F2v本体标注latency=0同样不等于跨调度/数据通路的端到端0拍。`vsetivli`切换也未被证明是等待全部老指令完成的全局栅栏，不能以此强行解释所有等待。

四个S0的A从ROB入队到FU接受，旧R2为38/39/41/44拍，M1为19/20/25/26拍，说明此次软件确实改变并缩短了这四个调用的释放路径；但二者仍无输出竞争。全部40个M1 A的该间隔为19～91拍，包含调度、操作数等综合等待，不把某个间隔冒称fdiv或vadd自身延迟。不同刺激的这些间隔不是同镜像性能比较。

最合理的机制解释是：F2v竞争请求与VDOT的R输出在时间上错开，M1的RAW桥接链与issue选择共同影响相对位置。**已证明的是没有同时竞争；尚未直接观察的是每条F2v的grant/写回时刻及I2v/vialu释放时刻。** 因而不能进一步断言8条请求全部在某一拍之前排空，也不能给出“挪动N条指令必能重叠”的周期保证。
