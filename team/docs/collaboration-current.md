## 0. Issue 事件精简与历史恢复（2026-10-24 生效）

Issue #2 的**唯一实时职责**是叶级任务包的 GitHub 账号级认领、与其他 Agent 实际冲突的运行/共享输入保护、短暂发布窗口。每次编译/EMU 批次、审计阶段、性能数字、工具失败/恢复和一般交接说明应进模块 RESULT/CONTRACT/evidence 或计分板，不逐阶段向 Issue 发送 UPDATE。

- **通常只需三条协调评论**：① `WORK` 认领并声明实际可能冲突的文件、资源和受保护输入；② 候选实际准备推送时 `INTEGRATE-BEGIN`，直接包含原 `READY` 所需候选 SHA、测试级别与结果链接；③ 推送完成时 `INTEGRATE-END / DONE` 合并为一条，写明远端实际 SHA、窗口关闭、认领释放及残留运行。未推送而完成/暂停/放弃，使用单条 `DONE`/`PAUSE`/`CANCEL` 明确包与运行保护状态即可。
- **仅在协调事实改变时增加 `UPDATE`**：实质变更认领范围或跨账号接手者、开始或结束需要他人避让的长运行、增减共享资源/冻结输入、发现冲突及状态不明。写真实操作 ID、state/receipt 定位、保护范围和状态；未知保护不自动释放。相同保护跨普通包内阶段继续生效，不每次重发。仅用于阶段进度/已保存在 evidence 中的结果不得发 UPDATE。
- 各事件正文优先精简为字段和证据链接（通常数百字即可）；不设可能损失关键安全信息的硬字符上限，也不限制必要例外事件数量。操作 ID、叶级包 ID、含时区时间、作者、完整关键 SHA、范围/有效状态必须准确。不能用旧摘要或一条未覆盖的归档推测别人空闲。
- **历史归档**：2026-10-24 清理前完整 114 条原始评论（覆盖评论 ID `6359269495` 至 `6384214655`）在 [issue-2-full-comments-20261024.json](archive/issue-2-full-comments-20261024.json)，含原始评论 ID、作者、时间、正文和永久链接，归档 JSON 文件 SHA-256 为 `30036ef2b06a6260346d2fd85a9a4dfef881927ee33c2a3408b5389972db474a`。归档作为历史证据，**不代表实时存活状态**；删除后的旧评论链接可能失效，按评论 ID 检索归档。
- 经用户明确授权清理时，先完整归档、校验仓库可读，再发布覆盖到准确评论 ID 的 `SNAPSHOT`（列出全部未释放认领、未结束/待核实运行保护、未结束窗口和最后有效事件），回读后只删除已归档且明确不再承担实时协调职责的评论。**不能删除活跃 WORK、待核实保护、未关闭窗口或未归档的新评论**。清理本身不得推断别人的进程结束或解除认领。
- **跨轮恢复**：先读本约定、最新完整 SNAPSHOT 和之后所有事件；核对实际 Git、state/进程和真实输入。遇到快照遗漏、活动/保护冲突或历史交接争议，按归档中原评论 ID 回溯；不依赖被清理的评论 URL。仅以最后真实事件和本机事实判断当前状态。

## 2. WORK = 任务包认领

1. 先按[开发路线](development-route-current.md)当前规划的工程包和默认次序选包，每位 Agent 默认一个主要**叶级包**（如 `R2-S2`，不得以 `R2` 一次占用所有子包）。正常情况不重新规划整个项目；环境/缺项类包须注明具体影响的子项，有新依据时按路线调整子项。
2. **先读 Issue 的有效 WORK/READY/PAUSE、长运行与冲突记录**，确认同包、共享源码/生成器/接口、构建目录和同机重任务均无撞车；没有同账号有效 WORK 覆盖时再发布简短 WORK：唯一操作ID、包ID、@GitHub身份/Agent、工作区与基点完整SHA、实际文件/接口范围、受保护的运行输入与资源。没有的字段写“无”。
3. **发布 WORK 后回读**。不同 GitHub 账号竞争同一叶级包时，按 GitHub **评论 ID 更小的有效 WORK 优先**；后来者停止冲突工作，改选包或与先认领者明确拆成两个不重叠子包。评论不是原子锁，在启动重任务或创建新实验输入前再次检查真实活动；不可变运行输入不得修改，未知状态不当作空闲。
4. 包内可连续设计、实现、验证、提交，**不逐小步骤登记、不要求每天续认领或等待全员 ACK**。实质扩展文件/共享资源或换包才用 UPDATE，先检查新增冲突。S1/S2 是不同叶级包，但共用冻结的 `candidate.py` 时仍须协商，以独立 S1 模块为默认方案。
5. READY 表示候选已完成主要工作而**等待集成，认领仍有效**。DONE 表示结果已交付/采用/否决或已明确放弃，释放该包；CANCEL 表示取消；PAUSE 必须明确“认领保留/释放”、依赖阻塞及实际未终结的进程/运行保护。失联、超时、未推送不自动释放任务包。即使包释放，受保护运行仍独立保持，不能被别人停止或覆盖。

实际需要的 READY / UPDATE / DONE / PAUSE / CANCEL 仍使用同一操作ID、真实测试级别和证据链接；常规发布把 READY 信息并入 INTEGRATE-BEGIN、把 DONE 并入 INTEGRATE-END，详情按第 0 节执行；不要复制 stdout 或重复计分板。

**认领归属于经实际认证核实的 GitHub 账号，不属于某个聊天、Agent 实例或操作 ID。** 同一账号的不同 Agent／PPA 新轮次可自行接续该账号已认领的同一叶级包，**无需人工批准、无需仅因换会话而重发 WORK/UPDATE/逐轮转交**。新轮次仍需用自己的独立操作 ID 留证，在计分板／结果记录中引用原 WORK、实际成果和工作区；原账号的认领继续有效，直到 DONE/CANCEL/明确释放的 PAUSE。原有 WORK 的归属不会因新对话或任务投递而变更。

**不同 GitHub 账号要接管另一账号的有效认领，必须先获得用户明确授权**，并在 Issue 使用一次简短 UPDATE 说明原 WORK、获准接手的账号、交接证据、旧认领转交／释放及未结束保护；接手账号用 WORK 引用该事件。原账号自己释放后，其他账号正常认领已空闲包不视为“接管”，仍按普通 WORK 检查竞争。账号身份必须以实际 GitHub 登录／授权上下文核实，不能仅凭模型声明、Git 作者配置或评论正文冒认。

**同账号免人工交接不等于共享工作树免冲突检查。** 若旧 Agent、Codex／Worker 或仿真仍在写入，后续 Agent 不得同时修改其工作树、Git index、冻结输入或抢占资源；先核实真实停止／无冲突，再从可定位成果在隔离工作区续做。不因失联、超时、旧对话结束、PPA 已投递而自行终止旧任务或解除运行保护。实质变更资源保护范围或跨账号协调时才向 Issue 更新，普通同账号接续只在现有成果／计分板留痕。


## 3. 并行与失败恢复

独立工作区、Git index、可写输出是并行前提；只读固定快照测试与新候选可并行。不同包也可能争夺生成器、接口或同机 JVM/EMU/综合资源，只暂停真正冲突部分，不长期“占领模块”。Agent 恢复时须核实最新 Issue 事件、真实 Git 状态、输入/输出 state、日志和进程/Worker，不重复启动任务，不覆盖他人封存证据。

当首选包缺工具或运行输入时，仅将受阻步骤标记 BLOCKED，明确条件；按既定任务表选择其他**未认领、可独立推进**的包，不无限预检，也不转向比赛材料制作。

<a id="cross-round-handoff"></a>

**新对话／PPA 跨轮接续。** 沿用计分板“路线影响／接续”与 Issue，不另建记忆目录。完成一个有意义阶段就保存成果，收尾时写清“下一动作＋所需条件＋源码／结果／state 位置”；未推送或位于独立工作区的成果须有下一轮可找到的工作区定位和提交／补丁身份，个人路径放运行记录，Issue 引用该记录。聊天回复不算持久化接续。

下一轮先读根目录计分板近期记录及 Issue 最新完整摘要和其后事件；没有摘要时从原事件读起。定位同一任务的最后有效成果，再核实实际进程／Worker、输入和工作树。同一 GitHub 账号的新对话／PPA 轮次可按第 2 节直接接续该账号的有效 WORK，不需要旧 Agent 额外发 UPDATE 许可；但同账号并不证明旧执行者已退出。必须核实旧执行者、Worker、受保护输入、Git index 与工作区状态；仍在写入或状态不明时只做独立非冲突工作，不重跑、不抢占，也不假定原 WORK 释放。新轮次用自身操作 ID 在实际成果／计分板关联旧 WORK。不同账号接管有效认领才需用户明确授权及 Issue 转交事件。Issue 不可用时仍保存本地计分板与成果，但不绕过跨账号认领冲突或共享分支发布协调。

## 4. 短暂集成窗口，仅推送时开启

1. 窗口外完成实现、主要验证、提交及准备；通常不另发 READY，而在短暂 INTEGRATE-BEGIN 中给出候选SHA、改动范围、实际测试和在途任务链接；确需长期保持待发布认领时可单发 READY。**长构建/仿真不占据窗口**。
2. 共享 `zufan` 推送须有当前用户授权。实际集成人确认其他未结束窗口及最新远端后发布 INTEGRATE-BEGIN（操作ID、目标、预期远端完整SHA、候选和验证摘要），**发布后立即回读最新窗口和活动，确认自己是唯一有效发布者后才可推送**。窗口只排他协调远端写入，别人继续本地工作。
3. 同一目标同时竞争窗口时，较小 GitHub 评论ID的有效 INTEGRATE-BEGIN 优先；后来者用 INTEGRATE-ABORT 释放自己的申请，继续窗口外工作。已存在窗口、首次同步未完成或状态不明时须由真实参与者核实，失联或过了预计时长不自动抢占。远端变化或必须长时间重验，先 INTEGRATE-ABORT，退出窗口到本地准备后重申请。
4. 推送前再次回读窗口与相关活动，并核对最新远端、合并影响及验证。只正常快进推送，失败先核实远端，不强推、盲目重试或丢弃他人提交。成功 INTEGRATE-END，记录远端真实SHA及验证；失败 ABORT 记录可能发生的远端副作用。
5. 发布完成不等于功能、DiffTest、PPA、成员复现或人工 ACK 都通过；发布时已确认交付与认领释放的，合并 INTEGRATE-END / DONE 一条；尚未确认交付则后续另发 DONE，未知状态不能提前释放。

Issue 不提供 Git 原子锁；Git FF 防止历史被覆盖，但不代替语义/合同检查。原先旧 START→RELEASE→ACK 不是每项普通工作的要求，已有未结束的历史发布必须核实。

## 5. 单一职责和试运行

[开发路线](development-route-current.md)只管包、次序、前置和决策；**Issue 只管实时任务认领、运行保护、集成窗口**；[开发计分板](../../开发计分板.md)记录每段有意义工作的时间、GitHub 身份、结果和证据；细节只在模块报告和实验目录。评论过长时允许 SNAPSHOT，标明覆盖到的评论ID/链接，列齐**全部未释放认领（含 READY 和 PAUSE 保留）、全部未结束或待核实的运行保护、全部未结束窗口**，并链接各项最后有效事件。DONE/CANCEL/释放认领的 PAUSE 所遗留的运行也必须保留；之后的评论仍生效，不建立第二张持有人表。

恢复时从最新完整摘要加其后评论读取；摘要缺项、相互矛盾或保护状态不明时回读原事件，不能把未列入摘要当成已释放。

首次真实双 Agent 试运行需验证：异包并行、同包竞争、不同包共用生成器冲突、失联恢复、远端变化后的安全发布与双方记录保留。**目前只是方案，尚未执行真实双人试运行**。
