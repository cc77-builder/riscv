# 三人两线协作机制（2026-10-13 更新版）

> 本文是 **团队协作流程的当前推荐执行约定**，由 2026-10-13 讨论更新。它不代表已合并分支、已认领工作包、已建立互斥锁、已运行回归，也不授权 Agent 读取本文后自动启动任务。实际开始由团队成员明确确认，所有动作遵循当前任务授权。

## 1. 目标、仓库与分支

- 目标：三位成员尽量并行开发与独立验证，降低冲突和交接成本；不为管理协作耗费 GitHub Actions 运行分钟。
- **唯一上游/canonical 仓库**：`cc77-builder/riscv`。任务责任、当期交接和验收以团队实际约定的一个位置为准，不在个人 Fork 复制一套“正在执行”状态。
- **个人 Fork**：`LiZufan001/riscv` 用于 ChatGPT 读取、研究和按需备份/同步。Fork 不是实时镜像，更不是第二个可独立认领同一共享分支的协调中心。
- 目标为**两条活跃开发线**：`zufan`（拟由原 `zjhwork` 成果合入后供两人共享）和 `James_Hotten`（另一条活跃线）；`main` 继续作为稳定集成线，单独计数。
- 当前 `zjhwork → zufan` 已完成 G-M1/G-M2/G-M3 复验及团队/Fork 发布，发布窗口由用户确认双方无人开发（见 [发布记录](../merge/2026-10-13-zjhwork-into-zufan.publication.md)），详见 [合并执行任务单](../merge/2026-10-13-zjhwork-into-zufan.md)。旧分支保留用于追溯，不删除、不覆盖历史；后续开发使用共享 zufan。
- H（硬件接入）/SV（语义、软件与验证）是**建议的工作分组**，不是按分支名锁定人员或模块。实际职责以团队认领的工作包和当前源码为准。

## 2. 四种责任必须分开

| 角色 | 说明 |
| --- | --- |
| 模块负责人 | 对工作包设计、交付和质量负责；不意味着一直占有推送权 |
| 当前执行者 | 此刻操作本地工作区、Codex、仿真/测试的人员或 Agent |
| 共享分支当前推送者 | 在一个明确交接窗口内唯一可推进团队 `zufan` 的人 |
| 独立验收者 | 针对固定代码 SHA 和明确证据审查；不能用“最新代码已通过”替代 |

任务卡只覆盖一个可验收工作包：ID、负责人、目标/边界、允许路径、依赖、状态（ready/active/blocked/review/verified）、起点 SHA、验收方式、下一步。Issue 可以使用，**但不是必需品，也不是锁**。工作包可以先保存在已有的团队进度文档中；不要同时维护两套主状态。

## 3. 真正并行的是工作区与测试，串行的只有共享远端分支写入

- 三个人各使用独立 clone/worktree 和独立构建/仿真输出目录。**绝不共享正在修改的工作树或 Git index**。正在跑长仿真时，固定源码快照、外部 NEMU 版本及输出目录。
- B 持有 `zufan` 推送窗口时，C 仍可在自己的本地任务分支准备补丁、对固定 SHA 做评审与测试；C 不直接 Push 团队 `zufan`。
- 热点接口/文件（译码、FU、写回、ISA 合同、版本锁）同一时段指定一名主修改者。越过已认领范围、修改公共接口之前先同步。
- 每位成员负责提交自己的局部测试与证据。独立复核由其他成员完成，不把全部验证和文档压给第三位成员。
- 本机 Codex 可以直接使用本地 Git 和文件；ChatGPT 借助 ChatPC 管理获授权的本机任务。两者无需把 GitHub Actions 当作中转或锁服务器。

## 4. START → RELEASE → ACK：最小交接协议

**START（开始/取得推送窗口）**
1. 读取 canonical 仓库的当前交接主记录、任务卡、远端 `zufan` 最新 SHA，确认上一人已 RELEASE、没有在途旧写入任务，下一人已明确接收。
2. 检查自己工作区的 dirty/untracked、本地未发布提交、子模块和外部 NEMU 状态；不得自动丢弃、stash 或重写他人工作。
3. 记录：`START | 执行者 | 工作包 ID | 允许路径 | 起始完整 SHA | 实际开始时间（含时区） | 关联 Codex 任务/回执 | 预计交接窗口`。**计划时间不是自动抢占期限**。

**RELEASE（提交并释放）**
1. 复核 diff 范围；按任务要求运行本机测试，明确通过/失败/未运行；记录源码 SHA、NEMU/submodule SHA、工具版本、命令、日志位置和未验证风险。
2. 从固定起点正常快进推送至**团队**共享分支，不使用 `--force` 或 `--force-with-lease` 当作日常交接手段。推送后重新查询远端 SHA。
3. 记录：`RELEASE | 执行者 | 最终完整 SHA | 变更摘要 | 测试状态及证据 | 未解决问题 | 仍在运行的任务 | 实际结束时间（含时区）`。没有完成验证时标注 WIP/未验收，不得声称完成。

**ACK（下一人接收）**
1. 下一人确认上一条 RELEASE、实际拉取并核实其最终 SHA，把自己先前在独立工作区准备的补丁整合到新起点。
2. 解决冲突并重跑受影响的测试，回复 `ACK | 接收者 | 已检出的完整 SHA | 任务范围 | 实际时间（含时区）`，然后再发布自己的 START。
3. 前任及其 Agent 在 RELEASE 之后不得继续推进这条共享远端分支。离线或失联时先保留成果并明确协商恢复，不能静默抢占。

**并发限制：** 评论/Markdown 记录本身不提供跨 Agent 强互斥；Git 的普通非快进拒绝只能防止覆盖，不能鉴别“谁有权 Push”。若两个 Agent 同时报 START、未确认释放、远端版本变化或存在不明后台任务，停止自动写入、比对当前状态后协调；不要重放失败的抢占记录。

## 5. Git 操作底线、PR 与验收

- 每次操作明确远端 URL 和目标分支；先 `git fetch`、读远端 HEAD，再确认本地提交包含最新远端 HEAD。正常 `git push` 被拒绝时停止并比对，不得直接强推或拿 `git pull` 掩盖冲突。
- 在共享分支上有待审 PR 时，冻结其 head；下一班仍可独立准备代码，但不能让新 Push 默默改变已评审版本。若确需更新 PR，重新按新 SHA 验收。
- 独立验收绑定精确 SHA、命令、配置和证据。组合 RTL 测试、主机模型测试、NEMU、全核 DiffTest、周期性能和 PPA 是不同层级，不互相冒充。
- 更新 `main` 是显式集成任务；不能为了方便而随手 rebase 已发布的共享分支历史。

## 6. 交接记录载体：低成本，单一真相源

**优先**使用团队所有人都可访问的单个 Issue/Discussion 作为交接记录，配合工作包卡片；若团队未启用这些功能，可选择团队仓库中的一份 Markdown 记录，并以普通 Git 快进提交更新。**选一种即可**，通讯群聊只发链接，不平行维护另一套“真实状态”。

Markdown 方案的 START 认领必须作为一次真实更新提交成功并再次验证远端 HEAD；两个候选同时写入时，只有经确认的有效记录可作为后续交接起点。失败者重新获取远端状态，不能把落败的 claim 简单重放/合并到赢家之后。

截至本文提交，**尚未创建实际的“持有人状态”或生效的机器锁，未指定真实执行者/班次**。Issue、Projects、Git 占用记录与机器人均不是当前必备设施。先运行两个完整交接周期，再决定是否需要额外的原子占用机制。

## 7. GitHub Actions：协作机制完全不依赖

- **不新增、不要求、不调用 GitHub Actions** 来管理任务卡、交接、分支同步、自动锁、RTL 测试或性能测试。
- 测试与仿真由成员已配置的本机/WSL/实验环境按需执行，记录可复现实验命令及结果；本方案本身不消耗 GitHub 托管 Runner 分钟。
- 仓库现有的 `.github/workflows/emu.yml`、`nightly.yml`、`perf.yml` 属于上游香山原工程参考资源；本次协作更新**不删除或改写**它们。它们是否会被触发、是否计费属于单独的仓库设置与 Runner 配置问题，不能仅因本方案写着“不依赖”就断言已被禁用。

## 8. 个人 Fork 的按需同步（非实时）

1. 通过**已授权、可访问团队私有仓库**的本机 Git 重新读取上游实际远端 SHA；GitHub 连接器暂时无法直接读上游时，可以使用 ChatPC 检查本机 Git 的正常授权访问。
2. 读取 Fork 对应分支 HEAD，验证是否相同，或 Fork HEAD 是否是上游目标 HEAD 的祖先。
3. 仅当可**正常快进**时将该上游分支同步到 Fork（显式分支、普通 Push，不 Force）；之后分别查询团队和 Fork 的远端 SHA 进行复核。
4. 若 Fork 含独有提交、分叉、目标已变化、权限异常：**停下来报告并先审差异**，不为同步牺牲 Fork 的独有成果。不要直接把 Fork 旧内容反向写回团队。
5. 同步是一次用户授权下的**按需操作**，不是后台实时镜像，也不是 START/RELEASE/ACK 状态锁。同步代码 SHA 不意味着 Fork 的 Issue/评论随之同步。

## 9. 落地范围与验收

- 2026-10-13 合并已发布到团队及 Fork zufan；这不代表真人职责已冻结或已建立机器互斥锁。
- 下一位明确工作包、核对已发布最终 SHA，在团队唯一交接载体记录 ACK/START，再推进共享分支。发布阶段已依据用户协调确认完成，不伪造下一位的接收记录。
- 试行两个完整交接周期后检查：代码覆盖/丢失为 0，共享工作树误写为 0，交接都有完整 SHA 与测试状态，成员不依赖私聊能找到当前执行者；如等待/维护成本偏高，先缩小交付批次而非添加后台服务。
