# 双人并发协作约定

更新：2026-10-23。两位开发者各带独立 Agent，独立工作区开发，最终集成到 `cc77-builder/riscv:zufan`。**以当前规划的工程任务包安排工作，Issue 负责认领和短暂推送窗口，不作为逐步骤审批。**

## 1. 启用状态

**唯一协调入口：[Issue #2](https://github.com/cc77-builder/riscv/issues/2)，已于 2026-10-23 获用户授权发布。首次成员活动同步待完成。** 两位实际成员取得同一版规则后，核对并在 Issue 登记各自已有任务、未结束发布窗口及受保护运行；没有则由本人说明，不代签他人 ACK。[登记模板](concurrency-issue-draft.md)仅供引用，不记录实时活动。Issue 已创建不表示双方已经同步或真实双 Agent 试运行通过；首次同步结果及其后的活动以 Issue 实际事件为准。

Issue 暂不可用时，只可继续已授权、确定不冲突的独立本地工作；空白评论、远端静止都不能证明队友空闲。共享分支发布或发生实际冲突时必须协调。文档不能自动授予 GitHub 写入权限。

## 2. WORK = 任务包认领

1. 先按[开发路线](development-route-current.md)当前规划的工程包和默认次序选包，每位 Agent 默认一个主要**叶级包**（如 `R2-S2`，不得以 `R2` 一次占用所有子包）。正常情况不重新规划整个项目；环境/缺项类包须注明具体影响的子项，有新依据时按路线调整子项。
2. **先读 Issue 的有效 WORK/READY/PAUSE、长运行与冲突记录**，确认同包、共享源码/生成器/接口、构建目录和同机重任务均无撞车；再发布简短 WORK：唯一操作ID、包ID、@GitHub身份/Agent、工作区与基点完整SHA、实际文件/接口范围、受保护的运行输入与资源。没有的字段写“无”。
3. **发布 WORK 后回读**。同一叶级包被同时认领时，按 GitHub **评论 ID 更小的有效 WORK 优先**；后来者停止冲突工作，改选包或与先认领者明确拆成两个不重叠子包。评论不是原子锁，在启动重任务或创建新实验输入前再次检查真实活动；不可变运行输入不得修改，未知状态不当作空闲。
4. 包内可连续设计、实现、验证、提交，**不逐小步骤登记、不要求每天续认领或等待全员 ACK**。实质扩展文件/共享资源或换包才用 UPDATE，先检查新增冲突。S1/S2 是不同叶级包，但共用冻结的 `candidate.py` 时仍须协商，以独立 S1 模块为默认方案。
5. READY 表示候选已完成主要工作而**等待集成，认领仍有效**。DONE 表示结果已交付/采用/否决或已明确放弃，释放该包；CANCEL 表示取消；PAUSE 必须明确“认领保留/释放”、依赖阻塞及实际未终结的进程/运行保护。失联、超时、未推送不自动释放任务包。即使包释放，受保护运行仍独立保持，不能被别人停止或覆盖。

后续 READY / UPDATE / DONE / PAUSE / CANCEL 使用同一操作ID，附实际测试级别、提交/证据链接与保护状态；不要复制完整 stdout 或重复写计分板。

需要交接时，由原执行者或获用户明确授权的实际成员用 UPDATE 明确旧操作ID、接手者、待续成果以及旧认领释放/转交状态；接手方 WORK 引用该事件并核对实际运行。接管任务不等于停止原进程或解除输入保护；这些保护只有在真实状态核实后才能更新。此规则仅用于交接，不增加普通包内审批。

## 3. 并行与失败恢复

独立工作区、Git index、可写输出是并行前提；只读固定快照测试与新候选可并行。不同包也可能争夺生成器、接口或同机 JVM/EMU/综合资源，只暂停真正冲突部分，不长期“占领模块”。Agent 恢复时须核实最新 Issue 事件、真实 Git 状态、输入/输出 state、日志和进程/Worker，不重复启动任务，不覆盖他人封存证据。

当首选包缺工具或运行输入时，仅将受阻步骤标记 BLOCKED，明确条件；按既定任务表选择其他**未认领、可独立推进**的包，不无限预检，也不转向比赛材料制作。

## 4. 短暂集成窗口，仅推送时开启

1. 窗口外完成实现、主要验证、提交及准备；READY 给出候选SHA、改动范围、实际测试及在途任务。**长构建/仿真不占据窗口**。
2. 共享 `zufan` 推送须有当前用户授权。实际集成人确认其他未结束窗口及最新远端后发布 INTEGRATE-BEGIN（操作ID、目标、预期远端完整SHA、候选和验证摘要），**发布后立即回读最新窗口和活动，确认自己是唯一有效发布者后才可推送**。窗口只排他协调远端写入，别人继续本地工作。
3. 同一目标同时竞争窗口时，较小 GitHub 评论ID的有效 INTEGRATE-BEGIN 优先；后来者用 INTEGRATE-ABORT 释放自己的申请，继续窗口外工作。已存在窗口、首次同步未完成或状态不明时须由真实参与者核实，失联或过了预计时长不自动抢占。远端变化或必须长时间重验，先 INTEGRATE-ABORT，退出窗口到本地准备后重申请。
4. 推送前再次回读窗口与相关活动，并核对最新远端、合并影响及验证。只正常快进推送，失败先核实远端，不强推、盲目重试或丢弃他人提交。成功 INTEGRATE-END，记录远端真实SHA及验证；失败 ABORT 记录可能发生的远端副作用。
5. 发布完成不等于功能、DiffTest、PPA、成员复现或人工 ACK 都通过；确认包已交付后用 DONE 释放认领。

Issue 不提供 Git 原子锁；Git FF 防止历史被覆盖，但不代替语义/合同检查。原先旧 START→RELEASE→ACK 不是每项普通工作的要求，已有未结束的历史发布必须核实。

## 5. 单一职责和试运行

[开发路线](development-route-current.md)只管包、次序、前置和决策；**Issue 只管实时任务认领、运行保护、集成窗口**；[开发计分板](../../开发计分板.md)记录每段有意义工作的时间、GitHub 身份、结果和证据；细节只在模块报告和实验目录。评论过长时允许 SNAPSHOT，标明覆盖到的评论ID/链接，列齐**全部未释放认领（含 READY 和 PAUSE 保留）、全部未结束或待核实的运行保护、全部未结束窗口**，并链接各项最后有效事件。DONE/CANCEL/释放认领的 PAUSE 所遗留的运行也必须保留；之后的评论仍生效，不建立第二张持有人表。

恢复时从最新完整摘要加其后评论读取；摘要缺项、相互矛盾或保护状态不明时回读原事件，不能把未列入摘要当成已释放。

首次真实双 Agent 试运行需验证：异包并行、同包竞争、不同包共用生成器冲突、失联恢复、远端变化后的安全发布与双方记录保留。**目前只是方案，尚未执行真实双人试运行**。
