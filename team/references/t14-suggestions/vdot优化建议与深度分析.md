# vdot 后续优化建议与深度分析

> **作者**：项目协助分析  
> **日期**：2026-10-16  
> **基于**：T12 全核回归通过版本 `2c0bf8e`、T13 性能报告 `4526d85`、T14 融合优化 `2443fb1`  
> **定位**：独立第三方视角的技术建议，供团队评估与讨论

---

## 0. 核心判断

读完项目的全部规格文档、RTL 设计、性能实测数据和测量方法论后，我认为**当前项目最大的问题不是"vdot 不够快"，而是"加速比的叙事结构还没有对准评委关心的东西"**。

团队在工程执行力上已经远超预期（计划 10/29 完成 T13，实际 10/15 就闭环了），但从评分角度看，现有 T14 的输入级融合优化虽然技术上正确，**方向选择的性价比不高**——它解决的是 FU 内部延迟从 3→2 周期，但 T13 数据已经清楚表明，全核瓶颈并不在 FU 的 3 个周期上。

下面按优先级给出我的建议。

## 1. 最应该做的事：不是更快的硬件，而是更好的故事

### 1.1 评分权重分析

回顾评分结构：

| 评分项 | 分值 | 当前覆盖程度 |
|---|---:|---|
| 阶段一完整性 | 15 | ✅ 充分 |
| 阶段二完整性 | 20 | ✅ 充分 |
| 阶段三完整性 | 25 | ✅ 充分 |
| 技术路径合理性 | 10 | ⚠️ 有设计文档，但缺少"为什么这样做比其他方案好"的对比论证 |
| 功能验证有效性 | 10 | ✅ 充分（T12 矩阵、故障注入、完整 128 位比较） |
| 微架构优化分析 | 5 | ⏳ T14 进行中，但优化点的微架构归因还不够深 |
| 软硬件协同理解 | 5 | ⚠️ DiffTest 工作已做，但缺少"差异定位案例"的叙事 |

| 扩展应用潜力 | 5 | ⏹️ 尚未开始 |

**我的判断**：60 分的完整性已经拿稳。剩余 40 分里，"技术路径合理性"（10 分）和"软硬件协同理解"（5 分）是当前最容易提分的点——它们不需要写新硬件，而需要写好分析。

### 1.2 具体建议：编写一份"设计决策白皮书"

在报告中加入一节专门的 **"设计备选方案与选型论证"**，内容包括：

1. **为什么选择非流水单发射而不是全流水**：引用 T13 数据，batch-128 时 vdot 的 4.68 周期/点积已经接近 FU 的 min_ii=4（基线版），说明当前调度/发射/写回开销才约 0.68 周期，全流水化的收益空间有限，而面积和时序代价不可忽视。
2. **为什么挂在 VFEX4 而不是新建执行端口**：新端口需要改 Rename、Scheduler、Datapath、WbArbiter，风险极大且本赛题不是比谁改的多，而是谁改的对。挂在 VFEX4 复用了成熟的 busy/反压/写回仲裁链路。
3. **为什么结果用 32 位而不是截断到 8 位**：数学上 8 项 int8 乘积和的范围是 `[-130048, 131072]`，19 位都不够表示正端点，8 位截断完全错误。这体现了对 ISA 语义的深刻理解。

这些内容团队其实已经想清楚了（我在 `rtl-interface.md` 和 `vdot.md` 里读到了非常扎实的论证），但它们散落在技术文档中，**还没有被提炼成面向评委的叙事**。

## 2. 关于 T14 优化方向的反思

### 2.1 当前融合优化的真实收益分析

T14 的输入-乘积级融合将 FU 延迟从 3→2 周期、min_ii 从 4→3。但让我们看看这在全核级别意味着什么：

```
T13 依赖链 n=256 数据：
  vdot: 2114 周期 / 256 点积 = 8.26 周期/点积
  FU 基线延迟: 3 周期（E0→valid），min_ii: 4 周期

  全核开销 = 8.26 - 4 = 4.26 周期/点积（OG2、调度、读数、旁路、写回）
```

优化后 FU 延迟 2 周期、min_ii 3 周期。假设全核开销不变（这是乐观假设）：

```
  优化后预期: 3 + 4.26 = 7.26 周期/点积
  预期加速: 8.26 / 7.26 ≈ 1.14×（相对基线 vdot 本身）
```

对比 RVV：

```
  原加速比: 21.25 / 8.26 = 2.57×
  优化后: 21.25 / 7.26 = 2.93×
```

**改善幅度**：加速比从 2.57× 提升到约 2.93×，绝对值看起来不大。但这个方向是对的——评委看的是"你是否理解了瓶颈并做了有针对性的优化"，而不是绝对数字。

### 2.2 更有说服力的替代优化方向

> [!IMPORTANT]
> 以下建议并非否定当前 T14 的工作（它已经做完 FU 验证和 EMU 构建，不应丢弃），而是建议在 T14 消融数据收集完成后，**再追加一个更有叙事价值的优化点**作为对比。

#### 方向 A：响应阶段旁路接收（RESP-cycle overlap）

**现状**：当前状态机在 RESP 握手完成后回到 IDLE，下一拍才能接受新请求。这意味着即使下游 ready 始终为 1，从一个请求完成到下一个请求开始至少隔了 1 个空闲周期。

**优化**：在 RESP 状态，如果 `out.fire` 和 `in.valid` 同时为真，同拍完成旧请求的输出并接受新请求的输入。这将 min_ii 从当前值再减 1（基线从 4→3，融合版从 3→2），而且 **不改变算术通路、不影响时序关键路径**。

**风险**：中等。需要处理同拍 redirect 与新接受的竞争、旧请求 robIdx 清除与新请求 robIdx 保存的时序。但概念上类似于经典处理器设计中的"EX/WB 旁路"。

**叙事价值**：极高。这个优化针对的是 T13 数据中可观察到的"FU 空闲间隔"，可以直接引用性能数据和波形来论证动机。

#### 方向 B：目的寄存器 bypass 写回（绕过 WbArbiter 延迟）

**现状**：VDot 的结果通过 WbArbiter 仲裁后写回向量寄存器文件。当同一周期有其他 FU 也要写回时，可能被延后一拍。

**分析**：T13 的 batch 场景中（四路独立点积，目的寄存器不同），vdot 的理论吞吐应该很高，但实测只有约 1.09×～1.13× 的加速。如果用波形观察到写回仲裁确实引入了气泡，这就是一个有数据支撑的优化目标。

**可行做法**：如果 VFEX4 端口的写回优先级可以通过参数调整（不需要改 WbArbiter 本身），这是一个低风险的配置优化。

**叙事价值**：高。直接回答了"为什么 batch 场景加速比不如依赖链"这个 T13 中提出但未深究的问题。

#### 方向 C：不做硬件改动，做一个纯软件优化的对比

**思路**：写一个"优化版 RVV 基线"——利用指令调度、减少配置切换、利用 `vwmacc` 等融合乘加指令——然后展示即使 RVV 基线被优化后，vdot 仍然有不可替代的优势。

**叙事价值**：极高。这直接证明了"自定义指令的价值不仅在于替代一组已有指令，更在于提供了已有 ISA 无法表达的语义压缩"。评委最关心的不是你能跑多快，而是你是否理解为什么自定义指令有存在的必要性。

## 3. 关于 T15 参数扩展的建议

### 3.1 推荐选择：int16 × 4 对（而不是 int8 × 16 对）

执行计划 §9.2 提到了两个候选：8 对 int16 或 16 对 int8。我推荐 **4 对 int16**，理由：

1. **对准实际应用**：LLM 推理中 INT8 量化后经常需要做 INT16 的中间累加。4 对 int16 × int16 → int32 是一个比 8 对 int8 更接近实际工作负载的配置。
2. **复用现有乘法器**：当前 8 个 8×8 乘法器可以直接重配为 4 个 16×16 乘法器（每个 16×16 用 4 个 8×8 构成），加法树从 8 项缩减为 4 项，逻辑量变化不大。
3. **边界清晰**：4 项 int16 乘积和的范围是 `[-2,147,516,416, 2,147,614,720]`，刚好在 33 位有符号内，用 64 位结果字段即可。这个数字比 8 对 int16 的 35 位更容易处理。
4. **展示参数化能力**：关键不是扩展本身有多复杂，而是能展示"修改 PAIRS 和 INPUT_BITS 参数后，模型、RTL、NEMU 和测试能自动适配"的工程成熟度。

### 3.2 扩展的验证策略

| 层次 | 验证内容 | 时间预算 |
|---|---|---|
| Python 数学模型 | 参数化 `INPUT_BITS=16, PAIRS=4`，重跑边界和随机 | 1 小时 |
| RTL 算术单元 | 修改 VDotDatapath 参数，重新 elaborate 并跑 Verilator | 2 小时 |
| FU 包装层 | 保持状态机不变，只改数据位宽和合法配置检查 | 2 小时 |
| NEMU | 在 vdot.h 中增加一个 `case` 分支 | 1 小时 |
| 全核 | **明确标注为"仅完成单元级验证"** | 0（不做全核） |

> [!WARNING]
> 不要尝试在截止日期前让扩展配置跑通全核。按照团队自己在 vdot.md §3.4 中的严格标准："只有完成扩展编码、全核译码、NEMU、DiffTest 和软件调用"才能宣称完整处理器支持。单元级通过就足以得到"扩展应用潜力"的评分。

## 4. 关于报告与答辩的建议

### 4.1 用数据讲故事，而不是罗列数据

T13 报告中有 1,404 个性能窗口、13 个校准窗口、39 个配对配置。这些数据的**体量本身就是一个巨大的优势**——但在报告中不能让评委自己去 CSV 里找结论。

建议报告的性能章节按如下结构组织：

```
1. 一句话结论（依赖链场景 2.57×，批处理场景 1.13×）
2. 为什么不同场景差异这么大？（图：横轴为场景，纵轴为加速比，标注瓶颈归因）
3. FU 级延迟 vs 全核延迟的差距说明了什么？（图：分解周期来源）
4. 优化前后的消融对比（T14 数据）
5. 我们没有做什么、为什么不做（Fmax、面积、功耗——诚实地说明仿真环境的局限）
```

### 4.2 DiffTest 差异定位案例

评分项"软硬件协同理解"要求"差异定位案例"。T12 中其实已经有很好的素材：

- 负控制测试中，bit100 翻转被 DiffTest 精确定位到对应的 vdot PC 和目的寄存器——**这就是一个完美的差异定位案例**。
- NEMU 的 `vdot_tval.h` 中对 trap 值的特殊处理——说明了为什么自定义指令的协同仿真需要参考模型和 RTL 在异常行为上精确对齐。

建议在报告中用 **"案例研究"** 的形式展开一个具体的 DiffTest 失败→定位→修复→回归的完整过程。哪怕是一个早期开发中遇到的 bug，只要能讲清楚机制，就是强有力的证据。

### 4.3 答辩准备

建议准备三个层次的演示：

1. **30 秒版**（电梯演讲）：一条自定义指令替代 5～7 条 RVV 组合，在依赖链场景获得 2.57× 的周期加速比，通过完整 DiffTest 协同验证。
2. **5 分钟版**（核心展示）：展示波形中一条 vdot 从译码到写回的完整生命周期，对比同一输入的 RVV 序列需要多少个周期完成同样的工作。
3. **15 分钟版**（完整答辩）：覆盖设计决策、实现细节、验证方法、性能分析和局限性。

## 6. 一些可能被忽视的细节

### 6.1 cycle 计数器的溢出问题

T13 校准数据中我注意到 `cycles=12531498870459704229`——这个数字已经超过了 `2^63`。虽然团队在 measurement.md 中明确说了"使用 Python 整数"和"禁止经过 JavaScript Number 或浮点再保存绝对值"，但在最终报告中如果使用 Excel 或 Google Sheets 做图表，**float64 精度丢失是一个真实风险**。建议：
- 所有原始数据保持 JSON 整数格式
- 图表只使用差值（已经远小于 $2^{53}$）
- 在报告中显式说明这一点，体现精度意识

### 6.2 首次访存样本的解释

T13 报告诚实地披露了首次访存场景中 vdot 更慢的情况（n=1 时 161 vs 130 周期）。这个现象的可能原因是：vdot 的测试代码在 AB 交替中先执行，触发了首次缓存缺失；而 RVV 后执行时命中了缓存。

**建议**：如果有时间，做一组 BA 交替（RVV 先执行）的对照实验。如果 BA 中 RVV 也出现类似的首次变慢，就证明这是实验顺序效应而非 vdot 的固有劣势。这种控制变量的实验设计会给评委留下很好的印象。

> 补充：我看到 measurement.md §3 已经说了"顺序按 AB/BA 交替"，并且 T13 报告 §5 也披露了这一点。这个实验设计本身已经很好了，建议在报告中更突出地强调这个对称设计。

### 6.3 关于 Verilator 仿真的局限性声明

团队在多处文档中反复强调"不推断 Fmax、面积、功耗"——这是正确的。但我建议在报告中**主动提供一段定量估算**，而不是只说"不知道"：

- 8 个 8×8 有符号乘法器在 TSMC 28nm 下的典型面积约为 1000 ～ 2000 μm²（可以引用公开的 RISC-V SoC 设计文献）
- 加法树的面积更小
- 相对于整个香山 CPU 核的面积，这个 FU 的占比应该在 0.1% 以下

即使是粗略估算，也比"不做评价"更有说服力。只要明确标注是估算、引用文献来源、不宣称等同于综合结果即可。

## 7. 总结

这个项目的工程执行已经非常出色。我的核心建议可以浓缩为三句话：

1. **先写好故事，再做新硬件**——报告的叙事质量可能比多 0.1× 的加速比更影响评分。
2. **T14 消融做完后，不要再追求更低的 FU 延迟**——全核瓶颈不在那里，把精力放在解释"为什么批处理场景加速比不高"上。
3. **T15 选一个小而完整的扩展**——4 对 int16 的单元级验证，加上清晰的参数化文档，比一个半成品的 16 对 int8 全核集成更有得分价值。
